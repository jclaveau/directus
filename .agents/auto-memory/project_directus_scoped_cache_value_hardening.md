Post-review hardening on `work-pr205` (branch `v11.10.1-feat/scoped-cache-value-tags`), all green + blackbox-covered. Builds on [[project_directus_scoped_cache_design]] / [[project_directus_scoped_cache_tag_derivation]].

- **Snapshot committed rows, NOT the payload** (the unifying principle across create/update/delete/upsert). The in-memory post-hook payload isn't authoritative: a DB default (omitted column), a `BEFORE INSERT` trigger, a generated column, or type coercion can diverge → tagging the payload value purges the WRONG slice → stale HIT. `snapshotScopedCacheTags(returnedKeys)` re-reads `SELECT scopeFields WHERE pk IN (keys)` post-commit. createMany + upsertMany now use it (mirroring updateBatch/deleteMany).
- **Collection-scoped fallback** — `purgeScopedCache(null)` was whole-namespace `cache.clear()`; now `purgeCollectionScope` cursor-SCANs `ns:tag:<coll>` + `ns:tag:<coll>:*` and purges only those tag sets. The `:` delimiter keeps a prefix sibling (`articles_archive`) out of `articles`'s scan. Also swapped `versions.ts` save flush.
- **Self-reference guard** — a read pinned to a value slice is sound only if the filter bounds every returned row. A self-ref relation (root collection at >1 field-map path, e.g. `parent.*`) pulls unbounded same-collection rows → tag BARE, not slice.
- **null sentinel** `\x00null` (not `String(null)='null'`) so SQL NULL never collides with a literal `"null"` string. The number/string collapse (`7`/`"7"` → same key) is INTENTIONAL + load-bearing: a REST string filter must resolve the numeric DB value's slice.
- **Value canonicalized BY FIELD TYPE (2026-07-02, deep-review follow-up)** — plain `String()` collapses number/string but DIVERGES for non-string scalars: boolean `true`(filter) vs `1`/`0`/`t`(sqlite/mysql/pg row), datetime ISO-string vs `Date`, decimal `1.5` vs `'1.50'` → read-side and purge-side derive DIFFERENT keys → stale HIT. Fix: `ScopedCacheTag.type` rider (@directus/types) carries the schema `Type`; `canonicalScopedCacheValue(value, type)` collapses both sides identically — boolean→'true'/'false', date/dateTime/timestamp→epoch ms, decimal/float→`String(Number())`. **integer/bigInteger keep `String`** (precision past MAX_SAFE_INTEGER; already collapse); **time stays string**; **extension tags (`cache.scope`/`cache.purge`) carry NO type → `String`** (extension owns both sides). Types plumbed via `collectionScopedCacheFieldTypes` getter into `scopedCacheTagsFromRows` + `pinnedScopedCacheTagsFromFilter`.
- **`requireAll: boolean` → `onUnresolvable: 'coarse' | 'skip'`** — the null-return path (row missing a scope-field KEY) is DEAD from the sole caller (`snapshotScopedCacheTags` projects via explicit `.select`, so every key present → never null); it only guards a hypothetical unprojected-row caller. A create's real unresolvable-fallback is the separate `someRowTakenOver` count check, NOT this. Renamed for call-site clarity ([[feedback_boolean_param_naming_trap]]).
- **Pure-aggregate reads ARE bare-tagged (NOT a bug)** — a `count(*)` names no field, so its field map has only the root; `fieldMapFromAst`→`extractFieldsFromChildren`→`getInfoForPath(fieldMap,'other',[],root)` inserts the root entry UNCONDITIONALLY (before looping children), so `collectionsInFieldMap` always includes root → bare tag → a write invalidates it. Guarded by a blackbox regression test (warm count→HIT, mutate→MISS, witness→HIT).
- **PK mutation is impossible** → the "snapshot-by-old-key misses new slice" edge can't occur. `updateMany`'s `changesNothing(field)` returns true for `primaryKeyField` → PK stripped from `changedFields`, never written.
- **Only remaining coarse purge = hook-takeover** (`liveKeys > actionPayloads` — rows a create hook inserted whose keys we don't hold). REST-unreachable, unit-only.
- **updateMany aligned (2026-07-02)** — was deriving the new slice from the post-hook payload; now re-snapshots committed rows like create/upsert/updateBatch (same authoritative-row principle). Purge unit tests re-pointed (sequenced `responseOnce` old→A/new→B; untouched-scope → `arrayContaining`).
- **Redis cluster rejected at startup** — `assertScopedCacheRedisSupported()` (wired in `createApp` after `validateStorage`) throws if scoped mode + `useRedis().isCluster` (ioredis marks standalone `.isCluster=false` / Cluster `=true`). SCAN + multi-key DEL are single-node → fail loud at boot, not a silent stale HIT. Scan-time throw removed (redundant). Core `useRedis` only builds standalone, so it bites only a custom override.
- **Helpers renamed onto the scopedCache radical** — `purgeScopedCacheTagKeys`, `scanScopedCacheTagKeys`, `purgeCollectionScopedCache` ([[feedback_name_vocabulary_one_radical]]); throwaway key-string locals (`tagKey`) kept (renaming would collide with the `scopedCacheTagKey` fn).

**Why:** review flagged upsertMany full-flush, self-ref staleness, create-omit full-flush + a payload≠DB hole. **How to apply:** any new mutation path → derive purge tags from committed rows, not the payload; fallback = collection-scoped, never `cache.clear()`.
