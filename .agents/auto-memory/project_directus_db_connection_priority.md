PR #213 (branch `v11.10.1-feat/db-connection-priority-policy`). A Directus **policy** grants a list of named DB connections; requests route to the highest-priority one the user's policies allow. Concrete use: two pgbouncer pools over one Postgres so a small free pool can't starve premium.

**Shape:** `directus_policies.db_connections` (CSV) → unioned onto `accountability.dbConnections` inside the existing `fetchGlobalAccessForQuery` aggregation (no extra query) → `getDatabaseForAccountability` picks by priority at the `ItemsService` ctor seam (`items.ts:93`). Connections come from `DB_CONNECTION_<NAME>_*` env (full knex config, any client, `_PRIORITY`); base `DB_*` = the default pool, nameable via `DB_DEFAULT_CONNECTION_NAME` and always a candidate.

**Settled decisions — a fresh review should NOT re-raise:**
- Priority lives on the CONNECTION (env), not the policy — policy only grants the set.
- Duplicate/colliding connection name → `getDatabase()` THROWS (fail boot), not warn.
- Pool-exhaustion → ONE `DatabasePoolExhaustedError` (429 + Retry-After) with a machine-readable `reason` enum (`client_pool_timeout`|`pool_queue_timeout`|`max_client_connections`|`too_many_connections`), not N classes. 429 (not 503) chosen deliberately. **Integration coverage:** bb `db-connection-priority.test.ts` has TWO real exhaustion cases — a knex/tarn `pool.max=1` acquire timeout (`client_pool_timeout`) AND a real **pgbouncer** service in `docker-compose.yml` (transaction mode, default_pool_size=1, query_wait_timeout=1s, host port 6109, digest-pinned 1.25.2) routed via a named connection → `pool_queue_timeout`. Added after jean flagged the tarn-only test as faking the pgbouncer use case ([[feedback_no_fake_integration_coverage]]). The pgbouncer service runs a **mounted config** (`tests/blackbox/pgbouncer/pgbouncer.ini` + `userlist.txt`, entrypoint overridden to `/usr/bin/pgbouncer <ini>` since edoburu otherwise regenerates from env) with **THREE pools over the same db**: `directus_free` (pool_size=1), `directus_premium` (4), `directus_default` (50); `query_wait_timeout=1s`, `max_client_conn=1000`. Named connections point at the one pgbouncer host (6109) with a per-tier `_DATABASE` override. Tests: `pool_queue_timeout` rides the tiny free pool (2 conns → queue → 429); and **pool ISOLATION** (`describe('DB connection pool isolation')`, the feature's real value) — a `/db-connection-probe/isolation` endpoint holds pool(s) saturated (fire sleeping queries, no await) then probes another in the SAME request; asserts saturating free doesn't starve premium, and free+premium doesn't starve the large default, each with a **non-vacuity control** (the saturated pool's own probe must fail). Validated locally at the knex level (isolated probe ~6ms; saturated pool times out). `max_client_connections` is now **unit-only too** — it needs a LOW global `max_client_conn`, incompatible with the many concurrent clients the isolation tests need (pgbouncer's cap is global, not per-pool). `too_many_connections` (pg 53300) stays unit-only (can't exhaust the shared backend safely). CI: `.github/workflows/blackbox.yml` has a `Start pgbouncer` step gated `if matrix.vendor == 'postgres'` (the vendor-up only starts the matrix service). bb is NOT push-gated on this feature branch but `blackbox-pr.yml` (name "Check") fires on `pull_request: synchronize` + the standing `Run Blackbox` label → every push re-runs it.
- Detection is **per-dialect** — folded INTO the postgres `dialects/postgres.ts` `extractError` (`getPoolExhaustedError`: pg `53300` by code, tarn/pgbouncer by message; returns the built `DatabasePoolExhaustedError | null`, [[feedback_fold_classifier_into_builder]]) because pgbouncer fronts only postgres. **Refactored (0eed02c5e7) to the universal translator:** one dialect dispatch handles constraint AND pool errors. `translate.ts` splits into a PURE `extractDatabaseError` (no hook) + `translateDatabaseError` (= extract + `database.error` hook, write-sites). The error-handler runs `extractDatabaseError` on EVERY unknown error (dispatch-all → never misses a DB/pool error, incl reads; non-DB errors fall through `default: return error`) — a heuristic pre-check was rejected because it can false-negative and MISS DB errors. Parallel `pool-exhausted.ts` deleted.
- The `connection` tag comes from `req.accountability`'s routed name (handler decorates the returned pool error), not the actual failing pool — fine for request-path queries.
- `translateDatabaseError` full coverage: **integration-first** ([[feedback_integration_first_unit_fills_gaps]]) — bb for the 3 API-reachable branches (UNIQUE, CONTAINS_NULL via schema-alter, FK); unit tests (`translate.test.ts` + `dialects/*.test.ts`, synthetic driver errors) for the validation-shadowed rest to ~100% line. Fixed a latent bug: unmatched client returned `undefined` → now returns the raw error.
- Numeric pool knobs coerced in `constructDatabase` (runtime env-inject sends strings).

**CreateItem is already a batch helper** — `tests/blackbox/common/functions.ts` forwards `item` as the POST body and Directus `/items/:collection` accepts an array; seeds already batch (build array → one call). The per-item `.push((await CreateItem).id)` loops are intentional `MAX_BATCH_MUTATION` limit-tests — do NOT "optimize" them. See [[project_directus_blackbox_sharding]].
