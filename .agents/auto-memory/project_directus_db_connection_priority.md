PR #213 (branch `v11.10.1-feat/db-connection-priority-policy`). A Directus **policy** grants a list of named DB connections; requests route to the highest-priority one the user's policies allow. Concrete use: two pgbouncer pools over one Postgres so a small free pool can't starve premium.

**Shape:** `directus_policies.db_connections` (CSV) → unioned onto `accountability.dbConnections` inside the existing `fetchGlobalAccessForQuery` aggregation (no extra query) → `getDatabaseForAccountability` picks by priority at the `ItemsService` ctor seam (`items.ts:93`). Connections come from `DB_CONNECTION_<NAME>_*` env (full knex config, any client, `_PRIORITY`); base `DB_*` = the **base pool**, nameable via `DB_BASE_CONNECTION_NAME` (default value `'base'`, priority `DB_BASE_CONNECTION_PRIORITY`) and always a candidate. The base pool is the **floor**: at equal priority any granted connection outranks it (a grant *means* "use this instead of base"; priority only orders grants among themselves), so base wins only by strictly-higher priority or as sole candidate. Ties among grants break by name. Renamed from `default`→`base` (jean: "default" implies override; a grant layers, not overrides — and `getBaseDbConfig` already used the `base` radical).

**Settled decisions — a fresh review should NOT re-raise:**
- Priority lives on the CONNECTION (env), not the policy — policy only grants the set.
- Duplicate/colliding connection name → `getDatabase()` THROWS (fail boot), not warn.
- Pool-exhaustion → ONE `DatabasePoolExhaustedError` (429 + Retry-After) with a machine-readable `reason` enum (`client_pool_timeout`|`pool_queue_timeout`|`max_client_connections`|`too_many_connections`), not N classes. 429 (not 503) chosen deliberately. **Integration coverage:** bb `db-connection-priority.test.ts` has TWO real exhaustion cases — a knex/tarn `pool.max=1` acquire timeout (`client_pool_timeout`) AND a real **pgbouncer** service in `docker-compose.yml` (transaction mode, default_pool_size=1, query_wait_timeout=1s, host port 6109, digest-pinned 1.25.2) routed via a named connection → `pool_queue_timeout`. Added after jean flagged the tarn-only test as faking the pgbouncer use case ([[feedback_no_fake_integration_coverage]]). The pgbouncer service runs a **mounted config** (`tests/blackbox/pgbouncer/pgbouncer.ini` + `userlist.txt`, entrypoint overridden to `/usr/bin/pgbouncer <ini>` since edoburu otherwise regenerates from env) with **THREE pools over the same db**: `directus_free` (pool_size=1), `directus_premium` (4), `directus_default` (50); `query_wait_timeout=1s`, `max_client_conn=1000`. Named connections point at the one pgbouncer host (6109) with a per-tier `_DATABASE` override. Tests: `pool_queue_timeout` rides the tiny free pool (2 conns → queue → 429); and **pool ISOLATION** (`describe('DB connection pool isolation')`, the feature's real value) — the `/db-connection-probe/pool` endpoint (merged `/exhaust`+`/isolation`) saturates pool(s) (fire sleeping queries, no await — held) then probes pool(s) in the SAME request, with `onProbeError: 'report'|'propagate'` — `report` records each pool's ok/fail (200; isolation, the saturated pool's own probe failing is the non-vacuity control), `propagate` rethrows a failing probe → error handler → 429 (the exhaustion-reason contract). Asserts saturating free doesn't starve premium, and free+premium doesn't starve the large default. NB the held saturate queries `.catch()`-swallow, so the PROBE is the query that propagates in exhaustion mode. Validated locally at the knex level (isolated probe ~6ms; saturated pool times out). `max_client_connections` is now **unit-only too** — it needs a LOW global `max_client_conn`, incompatible with the many concurrent clients the isolation tests need (pgbouncer's cap is global, not per-pool). `too_many_connections` (pg 53300) stays unit-only (can't exhaust the shared backend safely). CI: `.github/workflows/blackbox.yml` has a `Start pgbouncer` step gated `if matrix.vendor == 'postgres'` (the vendor-up only starts the matrix service). bb is NOT push-gated on this feature branch but `blackbox-pr.yml` (name "Check") fires on `pull_request: synchronize` + the standing `Run Blackbox` label → every push re-runs it.
- Detection is **per-dialect** — folded INTO the postgres `dialects/postgres.ts` `extractError` (`getPoolExhaustedError`: pg `53300` by code, tarn/pgbouncer by message; returns the built `DatabasePoolExhaustedError | null`, [[feedback_fold_classifier_into_builder]]) because pgbouncer fronts only postgres. **Refactored (0eed02c5e7) to the universal translator:** one dialect dispatch handles constraint AND pool errors. `translate.ts` splits into a PURE `extractDatabaseError` (no hook) + `translateDatabaseError` (= extract + `database.error` hook, write-sites). The error-handler runs `extractDatabaseError` on EVERY unknown error (dispatch-all → never misses a DB/pool error, incl reads; non-DB errors fall through `default: return error`) — a heuristic pre-check was rejected because it can false-negative and MISS DB errors. Parallel `pool-exhausted.ts` deleted.
- The `connection` tag comes from `req.accountability`'s routed name (handler decorates the returned pool error), not the actual failing pool — fine for request-path queries.
- `translateDatabaseError` full coverage: **integration-first** ([[feedback_integration_first_unit_fills_gaps]]) — bb for the 3 API-reachable branches (UNIQUE, CONTAINS_NULL via schema-alter, FK); unit tests (`translate.test.ts` + `dialects/*.test.ts`, synthetic driver errors) for the validation-shadowed rest to ~100% line. Fixed a latent bug: unmatched client returned `undefined` → now returns the raw error.
- **Env typing lives in the env layer, not downstream.** `packages/env` type-map has explicit per-key entries for `DB_CONNECTION_.+_PORT`/`_DATABASE` and base/named `POOL__*` (min/max/*_millis) → `@directus/env` casts them deterministically (guessType mis-handles leading-zero ports etc.). `cast` is now exported from `@directus/env`, and the blackbox **env-inject** test extension applies `cast(value, key)` on `/set` (it runs inside Directus, which resolves `@directus/env`) so an injected value is typed exactly like a real env var. This removed the old numeric-pool coercion loop in `constructDatabase` — jean: "prefer configured type definition per key if possible in the env layer". [[reference_directus_rest_batch_delete]] sibling context: the earlier comment claimed the coercion was for "unmapped env" — false, `create-env.ts:45` casts every process-env var (guessType fallback); the real gap was env-inject writing raw strings, now closed.

**CreateItem is already a batch helper** — `tests/blackbox/common/functions.ts` forwards `item` as the POST body and Directus `/items/:collection` accepts an array; seeds already batch (build array → one call). The per-item `.push((await CreateItem).id)` loops are intentional `MAX_BATCH_MUTATION` limit-tests — do NOT "optimize" them. See [[project_directus_blackbox_sharding]].

**PR #213 review round (settled — a fresh review should NOT re-raise):**
- **Vocabulary (renamed):** grant SET = `grantedDbConnections` (accountability + GlobalAccess; disambiguates from env registry `DB_CONNECTIONS`, [[feedback_disambiguate_colliding_names]]); merged pool-probe endpoint = `/db-connection-probe/pools-under-load`; resolve endpoint = `/granted`; helpers `grantedDatabase`, `GRANT_VENDORS`. Env `DB_CONNECTIONS` + column `db_connections` unchanged (external contract). "routed"→"granted" throughout ([[feedback_name_from_domain_vocabulary]]).
- **Finding #1 (fixed):** `extractDatabaseError(error, data, database?)` dispatches on the ROUTED connection's client (`getDatabaseClient(database)`), not the default — a named connection on another client is parsed by its own dialect. Write sites pass `this.knex`; error-handler passes the routed knex. Cross-client unit test in `translate.test.ts`.
- **Finding #2 (fixed):** error-handler resolve-then-tag — a pool error attaches `extensions.connection` on BOTH read AND write paths (`??=`, never overwrites). Write-path errors are already-Directus so they skipped the old tag block. Unit + bb assert it.
- **ExtensionsMap:** `DatabasePoolExhausted` registered in `packages/errors/src/types.ts` → `isDirectusError(x, code)` types its extensions → dropped the `extensions as {…}` cast ([[feedback_ts_as_cast_smell]]).
- **env-cast dedup:** `getConnectionPriority`/`getBaseConnectionName` = single-key `useEnv()` read + `typeof` guard; env type-map owns the cast, no downstream `Number()`/`String()` ([[feedback_trust_typed_boundary_no_recast]]).
- **DB_PUBLIC_SHARE_CONNECTION_NAME (new, shipped):** any `accountability.share` request routes to that named connection (must be configured, else ignored) → keeps anonymous share traffic off the base pool. Env-gated (unset = unchanged). Unit + bb tested (probe `/granted` takes a `share` marker). Type-map `string` entry + env-stub docs (dedicated capped pool, never premium).
- **Parked → issue #216:** policy-driven per-share pool routing (reuse `directus_shares.role` → its policies, no column). See [[reference_directus_share_auth]].
- **Kept casts (required, don't flag):** `error as SQLError` (unknown→parser boundary), partial driver-error fixtures (`as PostgresError` etc). The pool-error `connection` tag reflects the REQUEST's routing (admin→base), not the failing pool — by design.

**PR #213 review round 2 (2026-07-08, settled):**
- **Finding: admin `break` dropped grants (fixed).** `fetchGlobalAccessForQuery` short-circuits on the first admin policy (`if (globalAccess.admin) break;`); grant collection was in that same loop → policy rows after the admin row lost their `db_connections` (row order undefined, no ORDER BY → non-deterministic). Split into a **dedicated grants pre-pass** (full scan, same ip filter) BEFORE the admin/app loop, which reverts to its upstream shape. Regression test: admin row first + grant on a later row → grant survives.
- **Finding: grant names not trimmed (fixed).** `toArray` (CSV split) does NOT trim; registry side (`getExtraConnectionNames`) does → `"a, b"` grant → `" b"` never matched. Added `.trim()` in the pre-pass + test.
- **Finding: `DB_PUBLIC_SHARE_CONNECTION_NAME` leaked into knex connection config (fixed).** Not in `getBaseDbConfig` omit lists → passed through to every pool's knex `connection`. Added to `omitKey`.
- **Base-floor semantics (new, this round):** see the floor rule in the Shape paragraph. Reducer carries an `isBase` flag; equal-priority base loses to any grant. Behavior change from round 1 (grant used to need strictly-higher priority to beat base). Unit witnesses: equal-priority grant beats base; two grants tied at base priority break by name with base excluded.

**PR #213 review round 3 (2026-07-08, settled — merged as merge-commit `19953434ec` into `v11.10.1-hhh-dev`; repo uses `Merge pull request #NN` merge commits, NOT squash):**
- **Finding A (fixed): constraint error misread as pool exhaustion.** `postgres.ts` `extractError` ran `getPoolExhaustedError` FIRST, matching raw `error.message` substrings (`'pool is probably full'`, `'query_wait_timeout'`, …). A `23505` unique violation whose stored VALUE contained such a phrase (`Key (note)=(pool is probably full)`) returned `DatabasePoolExhaustedError` (429) instead of `RecordNotUnique` (409). Fix: move `getPoolExhaustedError(error) ?? error` into the switch **`default`** — a recognized SQLSTATE returns first, only code-less errors reach message matching. Regression test in `postgres.test.ts` (fails without the reorder). General principle: [[feedback_code_classify_before_message_substring]].
- **Finding B (fixed): bb probe route crash-safety.** `/pools-under-load` lacked the outer try/catch that `/granted` has ([[reference_bb_extension_route_crash]]) — `grantedKnex()` building a misconfigured named connection throws, a bare extension route has no async wrapper → unhandled rejection = shard exit. Wrapped the whole body → 500; the `next(error)` propagate path still works (next returns, doesn't throw).
- **Fix #2 (fixed): named-conn credential typing.** env type-map cast `_PORT`/`_DATABASE` but not `_USER`/`_PASSWORD`, unlike base `DB_USER`/`DB_PASSWORD` (explicit string). A numeric-looking password (`"12345"`→number) or `"true"`→boolean broke auth via `guessType`. Added `DB_CONNECTION_.+_(USER|PASSWORD)` → string; `_HOST`/`_CLIENT` left on guessType (base does too). Regression in `create-env.int.test.ts`.
