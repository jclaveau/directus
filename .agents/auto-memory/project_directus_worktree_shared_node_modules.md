Every `deps/.wt-*` worktree has

```
.wt-<name>/node_modules      -> deps/directus-cms-2/node_modules
.wt-<name>/api/node_modules  -> deps/directus-cms-2/api/node_modules
```

so `api/node_modules/@directus/specs` resolves through the real path to
**`directus-cms-2/packages/specs`** — the MAIN tree's copy, on whatever branch it
happens to be checked out at. `realpath api/node_modules/@directus/<pkg>` proves it.

**Symptom:** a test that touches another workspace package fails locally and is
green in CI. On #350, `specifications.test.ts > omits a path whose x-enabled-by
env flag is off` failed on `/utils/cache` because the spec it loaded had 24 tags
and no `System MCP` — the main tree's build, not the branch's. `packages/specs/dist/openapi.json`
inside the worktree was correct the whole time; rebuilding it and clearing
`node_modules/.vite` changed nothing.

**A local `tsc --noEmit` in a worktree is unreadable for the same reason.** `npx tsc -p api` on
PR #350 printed **201 errors**, nearly all cascading from one bad resolution — `@directus/types`
came from the main tree and lacked `CachePurgeMode` (added by #353), so every downstream
`Cannot find name 'CacheTimeseries' | 'CacheConfigEvent'` was noise. Two real errors of mine
were buried in it. The repo's CI has no tsc gate anyway (build is esbuild/tsdown, types are
stripped), so treat local tsc as a grep for YOUR file's new symbols, never as a pass/fail.

**How to apply:**
- Own-package tests (everything under `api/src` importing `api/src`) are
  trustworthy in a worktree. Anything crossing a `@directus/*` boundary is not.
- Baseline-diff before blaming your diff: `git stash push --include-untracked --`
  the touched dirs, re-run, `git stash pop` (stash is shared across worktrees —
  pop it back immediately, [[reference_git_stash_shared_across_worktrees]]).
- To really run it, use the main tree, or build the dependency package there.
  CI installs per-branch and is the arbiter.
- **Shadow trick (worked 2026-09-16, `@directus/utils/values` missing on the
  main tree's branch):** Node resolves upward, so an ignored
  `.wt-x/api/src/node_modules/@directus/utils -> ../../../../packages/utils`
  wins over `api/node_modules` for every import under `api/src`. Build that
  package in the worktree first (`ln -sfn <main>/packages/utils/node_modules
  .wt-x/packages/utils/node_modules && pnpm run build`). Same for
  `packages/env/src/node_modules/@directus/utils` to run the env tests.

**A NEW type added on the branch is invisible to vitest's own typecheck gate for the
same reason — worse than noise, it's a false "0 errors".** On PR #447, a new
`ProcessHostCapacity`/`capacity` field was added to `packages/types` on the branch, then
consumed elsewhere in the same worktree. `vitest`'s "Type Errors no errors" line was
worthless: `api/node_modules` symlinks to the main tree, so `@directus/types` resolved
to the **main tree's** copy with zero occurrences of the new field, and the vitest
typecheck gate additionally self-disables in a package with no `*.test-d.ts`
([[project_directus_vitest_typecheck_gate]]) — two independent reasons for the same
green. Caught only by re-running `tsc`/`vue-tsc` by hand with `paths` pointed at the
**worktree's own** `packages/types`/`packages/system-data` output, not the main tree's —
that run found a real break (an MCP test fixture missing the new required field) that
would otherwise have shipped. Any api-only remaining errors from that run
(`@types/pg`, `fast-check`, etc.) that are declared in the branch's own `package.json`
but absent from the shared `node_modules` are install-state artefacts, not code — CI
resolves them; don't chase them locally.

**`tests/blackbox`'s typecheck passes vacuously in a worktree.** `npx tsc --noEmit` there
aborts on `tsconfig.json(2,13): error TS6053: File '@directus/tsconfig/node22' not found`
— it checks nothing and you read the silence as success
([[reference_gate_can_pass_vacuously]]). It hid a real arity error (an extra argument to
`getNoCacheUrl`) until CI. Either read tsc's FIRST lines for tsconfig errors before
trusting a clean run, or verify the specific call against its signature by hand.

**The `app` vitest suite cannot start in a worktree at all.** Vite bundles
`app/vite.config.js` into `directus-cms-2/node_modules/.vite-temp/` and resolves that
temp file's bare imports from the ROOT `node_modules`, which holds none of them
(pnpm keeps them under `app/node_modules`): every run dies with
`Cannot find package '@directus/extensions'` before a single test collects. A
hand-written minimal `--config` fails identically (`@rollup/plugin-yaml` next). The
way through, measured on the autoscale-config GUI: **copy the touched app files into
the MAIN tree's matching directory, run `npx vitest run <dir>` there, then
`rm` the new files and `git checkout --` the tracked ones.** Type-only imports of a
branch-new `@directus/types` symbol are erased at transform time, so they cost
nothing — but every runtime dependency must travel too (copying `processes.vue`
without `processes-view.ts` gives `(0 , latestSample) is not a function`).

**`vue-tsc` is not an available instrument here either.** In the worktree the
`extends` chain to `@directus/tsconfig/vue3` does not resolve, so all 4408 "errors"
are one bad resolution (ES5 lib, no `Promise`, no `vue`); in the main tree the same
run is killed (rc=15) before it prints anything. The app has no tsc gate in CI —
`Check` is build + eslint + stylelint — so this costs nothing but do not read either
result as a signal.

**A worktree has no `packages/*/node_modules` at all, and an api dist built there is
garbage (PR #492, 2026-09-15).** Three walls in a row when a branch adds a package
subpath export:

- `pnpm --filter @directus/utils build` → `command not found: tsdown`: only the root
  and `api/` node_modules are symlinked, every `packages/<p>/node_modules` is missing.
  Symlink the ones you need from the main tree
  (`ln -s ../../../directus-cms-2/packages/<p>/node_modules packages/<p>/node_modules`).
- Then `ERR_PACKAGE_PATH_NOT_EXPORTED: Package subpath './values'`: the symlinked
  `packages/env/node_modules/@directus/utils` is the MAIN tree's copy, whose
  `package.json` predates the export. Replace that one entry with a hand-built farm
  whose `@directus/utils` points at the worktree's own `packages/utils`.
- An **unbundled** api build (`tsdown` with externals) from a worktree emits import
  paths like `dist/directus-cms-2/node_modules/…` — it followed the symlinks and
  wrote the main tree's real paths into the artifact; rc=1 and nothing runnable.
  A worktree cannot measure a dist (RSS, boot time). Say so in the PR instead of
  reporting a bogus number; the bench workflow measures on CI
  ([[project_directus_startup_bench]]).

**Run api tests against the BRANCH's own packages (2026-09-15):** a branch that adds
a subpath export (`@directus/utils/values`) fails every importing test with
`Missing "./values" specifier` because `api/node_modules/@directus/utils` is the
main tree's checkout. Drop an untracked `api/vitest.wt-values.config.ts` that
`mergeConfig`s the api config with `resolve.alias` regexes pointing each package
at the worktree — `@directus/utils/values` → `packages/utils/shared/values/index.ts`,
`@directus/utils` → `packages/utils/shared/index.ts`, and any dep that itself
imports the new subpath at its worktree **dist** (`@directus/env`,
`@directus/memory`, built with `pnpm --filter <pkg> run build`) — then
`vitest run --config vitest.wt-values.config.ts <files>`. Aliased paths outside
`node_modules` are inlined, so `vi.mock('@directus/utils', …)` still intercepts
them. Delete the config before the style gate (it scans untracked files). Copy
kept in the job scratch as `vitest.wt-values.config.ts`.
