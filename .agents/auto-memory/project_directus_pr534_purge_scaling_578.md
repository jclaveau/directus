**#534 (composite fingerprints, merged 5222b31ac5) slowed prod the night it deployed (2026-09-28, ~04:30 UTC, blow-up 05:45).** Worker CPU ~20% (more workers useless); purge p95 466 ms → 17-23 s; cache HIT 14 → 175 ms. Root cause: `SSCAN … COUNT 1000` over the BARE per-collection index sets (two of a consumer's collections, 100k+ members each) — MATCH doesn't cut the walk, one 10-36 ms command blocks all Redis clients; cost = set size/1000 × up to 64 globs × sets. Expired members leave only through the reap. Action taken by jean: `CACHE_ENABLED=false` + flush (index sets dropped, response entries left) — don't re-enable without a namespace change or a real response clear.

**Decision (jean): A+C+RNS in PR #578 (issue #570), one goal, one PR.** A = home-pin index sets (per-value, purge cost flat: 14 cmds at 1k and 100k); C = per-collection registry `collection-index-keys` replacing keyspace SCANs; RNS = register only the sets a fill creates (fan fill 56 KB vs 84.6 KB without it, ceiling 78 KB). B (pruning) and the hotfix DROPPED. Follow-ups: boolean home pin should prefer pk/unique fields (bug filed); reap ported to close the stranded-swept-set hole ([[project_directus_stale_cache_stranded_swept_sets]]).

**Deploy fill pause** (jean: "disable the writes in cache during deploys" instead of plumbing): a boot whose core build id differs from the recorded one sets `${ns}:scoped-cache-fill-pause` PX `CACHE_SCOPED_DEPLOY_FILL_PAUSE_MAX` (default 5m, ceiling, UNMEASURED); same-build replicas join via PTTL; `respond.ts` gates only the FILL (existing HITs still served); completeness-mark refuses during it; each node reaps at its end. `core-build-id.ts` exists because the autoscale graph test forbids the autoscaler reaching `@directus/utils`/db. Open idea, not built: end the pause when the processes report (already listed in the autoscaler admin page) shows no old-build process, instead of a timer.

**Bench findings:** the #534 deploy's CPU bump was visible in prod graphs but not in the bench; `--max-semi-space-size` 8→2 was questioned; bench issues filed (fork: tighten existing bench, no new one; consumer: pin-bump A/B). Purge bench ≈1 min max; fidelity test permanent at 1k. See [[project_directus_bench_measures_trunk]].

**Settled, don't re-raise:** epochs stay per collection (per-owner epoch = separate issue #532, has a documented parent-write race); telemetry column stays `scoped_cache_pin`; tag-only purge no longer exists (purge is fingerprint-based); fingerprints are objects in Node, serialized globs in Redis; caps (64 globs, pins) parked to the end; A+C stale risk judged LOW and only reachable across deployments (audit `stale` + purgesSinceFilled catches it).

**Index marker model (redis-store.ts, ~:937):** `complete = marker !== null && marker === generation`. Marker key `<prefix>collection-index-keys-complete` holds the generation the reap read; generation counter `<ns>:scoped-cache-index-generation` lives outside the prefix (survives drop). `dropIndex` DELs marker + INCRs gen; FLUSHDB reseeds gen from `TIME` so an old marker can't match; an older-build drop bumps the wholesale `'*'` counter, which the mark script also compares; mark refused while the fill pause exists. Check+SET in one Lua script. Accepted gap: an old-build node outliving the pause files unregistered sets AFTER the marker → collection purges miss them until next reap. Read path never reads the generation, so HITs survive a generation move (validates the HIT-during-pause bb test).

**Deploy-pause watcher + bb coverage (b4a7de2a13):** 3 quiet looks 5s apart via `collectProcessReports([])`, comparing `self.coreBuildId`; a report without it counts as the older build; `PROCESSES_REPORT_ENABLED=false` → pause runs to ceiling. `coreBuildId` is BUS-ONLY (not in `/utils/processes` nor `list_processes`; exposing it needs a `ProcessNode` + collect-processes.ts change, jean's call, not asked yet). Metric `directus_scoped_cache_index_reads_total{mode=registry|scan}`. Pause bb files cost ~90s (ceiling scenario). bb gotcha: a wait for the boot's reap placed in a Background runs before EVERY scenario; a scenario that deleted the marker by hand then times out (reap runs once a year in that test) → wait once at suite start.

Related: [[project_directus_issue531_composite_tags]], [[project_directus_prod_cache_measurement]].

**Reap lock race (reap-requests.ts:87, verified low, 2026-09-30):** claim is Keyv get→set, renew/release carry no owner token, Keyv fails open when the `_lock` tier errors, and `POST /utils/cache/clear` targets response+locks drops the lock right after `dropScopedCacheIndex` schedules a reap → two whole-index reaps can overlap. Cost = duplicate Redis work + a few spurious fill evictions (each pass INCRs the collection counter); NEVER a stale HIT (every reap write is one idempotent Lua script, marker compared to generation). Same shape as `cache-audit-runs.ts:148-150` (documented accepted), `system-cache-lock`, `telemetry-lock`. Disposition: disclose (copy the audit's two sentences + Keyv fail-open) or ioredis `SET NX PX` + token compare-and-delete. Lock lives in REDIS's shared DB, not CACHE_REDIS_DB, so the FLUSHDB-takes-the-lock claim is refuted. Review-run gotcha: a `/code-review max` fan-out of ~20 Opus verifiers hit the session 429 limit and all died; resume capped at 4 concurrent.
